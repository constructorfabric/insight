# Backend specs — under review

The specs below disagree with the code in the places listed. Read them against the code, not as authority, until each entry is closed.

| Spec | Do not trust until checked |
|---|---|
| [`authenticator/DESIGN.md`](authenticator/DESIGN.md), [`PRD.md`](authenticator/PRD.md) | The admin revoke-by-user variant is documented on `DELETE /auth/sessions`; that route is public and self-only, and the admin variant is a separate authenticated route. The DESIGN route table marks CSRF on `POST /auth/logout` only; the code checks it on every state-changing `/auth/*` request, `POST /auth/refresh` included. The session model has a `tenants` field and one PRD line still lists a `tenants` JWT claim; both are a single `tenant_id`. The listed metric names are not the ones the crate registers. Several documented status codes are redirects in code. |
| [`gateway/DESIGN.md`](gateway/DESIGN.md) | The hygiene list describes `auth_request` / `auth_request_set` and `error_page`; routegen emits neither — it uses `access_by_lua_block` and shapes failures in Lua. |
| [`identity-resolution/identity/specs/DESIGN.md`](identity-resolution/identity/specs/DESIGN.md), [`PRD.md`](identity-resolution/identity/specs/PRD.md) | Ambiguous-profile is documented as `422` with structured members; the service returns `409`. Subchart depth is documented as unbounded; it is capped and clamped. The subchart auth is documented as an `X-Insight-Person-Id` header; it is the gateway JWT. |
| [`domain/identity-resolution/specs/DESIGN.md`](../../domain/identity-resolution/specs/DESIGN.md), [`PRD.md`](../../domain/identity-resolution/specs/PRD.md) | **Understates the code.** The whole operator resolution surface (`/v1/resolution/{bind,merge,detach,exclude}`, `/attention`, the account and person-accounts reads) is marked planned but is registered, handled and published in the contract. Contested-evidence handling, per-account bindings in divergent groups, author-aware conflict classification and per-account timestamp disambiguation are all described as gaps or future work and are all implemented. Tombstone handling is called inert; DELETE rows are kept deliberately. Going the other way: the v1 resolve macro is described as e-mail-only — it resolves through account bindings and returns nothing when claimants disagree — and the "writes only to its own tables" claim omits `visibility`, `roles` and `person_roles`. |

The `openapi.json` next to each service is generated from the code and checked by CI, so where a spec and the contract disagree, the contract is right. Regenerate one with `(cd src/backend && cargo run -p <service> -- openapi) > docs/components/backend/<service>/openapi.json`.
